Дата: 2026-08-30, актуализировано 2026-09-03. Изначально документ писался на этапе
**проектирования**, до кода.

> **Статус реализации (запрос №34).** Реализованы и проверены: `/`, `/catalog`,
> `/catalog/category/:category` (8), `/catalog/:product` (50 маршрутов: 49 видимых + скрытый
> дубль), `/machines`, `/machines/:machineType` (7), `/contacts` (запрос №32),
> `/oplata-i-dostavka` (запрос №33). Итого 70 публичных страниц. Плюс `src/pages/404.astro`
> (запрос №34) — специальный документ ошибки: `dist/404.html`, вне навигации, вне sitemap,
> **не входит** в счётчик публичных страниц; `check-links.mjs` проверяет его существование
> отдельной строкой, а не через `EXPECTED_ROUTES`. `PLANNED` в `scripts/check-links.mjs`
> пуст. Не реализована только служебная `/_data-review` (отложена отдельным решением — на неё
> нет и не должно быть ссылок). Где реализация разошлась с этим документом, в тексте стоит
> пометка «Обновлено на этапе каталога» — побеждает код, документ приводится к нему. Текущее
> состояние целиком — `docs/HANDOFF.md`.

Источники: `data/content-inventory.json`, `data/content-map.csv`, `docs/inventory-report.md`,
`docs/REFERENCES.md`, `.claude/rules/*`. Числа в документе получены пересчётом инвентаря скриптом,
а не оценкой.

Решения пользователя, зафиксированные на этом этапе:

1. Категории каталога — провизорная группировка уровня прототипа (`provenance: "prototype-grouping"`).
2. DR-09 — один canonical Product + варианты по типу техники.
3. Stack — Astro + TypeScript, статическая сборка.
4. Canonical URL товара не содержит категорию.
5. Неподтверждённые записи (`confirmed: false`) не видны в пользовательском UI.
6. Фиктивный текст политики конфиденциальности не создаётся.

| Раздел | Причина отсутствия |

### Почему Product URL не содержит категорию

Категории — уровень прототипа, а не факт исходного сайта: их можно переименовать или переразбить
после ревью владельца. Если бы адрес товара выглядел как `/catalog/:category/:product`, любое
изменение группировки меняло бы постоянные адреса товаров.

Поэтому:

- `/catalog/kovsh-chelustnoy` — canonical, стабильный;
- `/catalog/category/kovshi` — отдельное пространство категорий;
- категория остаётся **навигационным контекстом**: в хлебных крошках, в фильтре каталога, в блоке
  «похожее оборудование», в метке на карточке товара.

`slug` товара берётся из `sitemap.xml` исходного сайта, поэтому адреса прототипа соответствуют
реальным адресам источника.

## 2. Навигация

**Header (одинаковый на всех страницах):**
логотип → `Оборудование` (`/catalog`) → `Тип техники` (`/machines`) → `Оплата и доставка` →
`Контакты` → телефон как кликабельная ссылка → кнопка «Запросить цену».

Выпадающих мега-меню нет: 8 категорий и 7 типов техники показываются на своих хабах и на главной.
Это упрощение по сравнению с источником, где `Оборудование` и `Тип техники` раскрываются
выпадающими списками — на мобильном они работают плохо.

**Mobile:** полноэкранное меню по кнопке-бургеру; те же 4 пункта + телефон + CTA.

**Footer:** контакты (телефоны, e-mail, Telegram, адрес, часы), колонка «Каталог» (8 категорий),
колонка «Тип техники» (7 типов), копирайт в формулировке источника. Ссылки на политику
конфиденциальности нет (см. выше).

**Breadcrumbs** — на всех страницах, кроме главной:

- `Главная / Каталог`
- `Главная / Каталог / Ковши`
- `Главная / Каталог / Ковши / Ковш челюстной` ← категория как контекст, в URL её нет

## 3. User Journey A — пользователь знает, какое оборудование ему нужно

```
/  →  блок «Два входа», карточка «Каталог оборудования»
   →  /catalog                       49 товаров, фасеты, счётчик
   →  /catalog/category/kovshi       11 товаров
   →  /catalog/kovsh-chelustnoy      canonical Product
   →  таблица характеристик          6 колонок, цены внутри таблицы
   →  «Запросить цену» (mock)        форма с предзаполненным названием товара
```

Ключевые детали:

- на `/catalog` фильтр «Категория» и переход в `/catalog/category/:category` дают **один и тот же
  результат**; категорийная страница — это каталог с предустановленным фильтром и своим H1/описанием;
- хлебные крошки на товаре ведут обратно в его категорию;
- CTA один и тот же на всех уровнях — «Запросить цену»/«Оставить заявку», без «Купить».

## 4. User Journey B — пользователь знает свою базовую технику

```
/  →  блок «Два входа», карточка «Подбор по типу техники»
   →  /machines                      7 подтверждённых типов
   →  /machines/minipogruzchik       35 совместимых товаров, теми же карточками
   →  /catalog/kovsh-chelustnoy?mt=minipogruzchik
                                     тот же canonical Product,
                                     вариант под минипогрузчик предвыбран
   →  таблица характеристик этого варианта
   →  «Запросить цену» (mock)        в заявку попадают товар + тип техники
```

Ключевые детали:

- **оба пути ведут на одну и ту же страницу товара** — дублирующих карточек «ковш на минипогрузчик»
  в прототипе нет;
- параметр `?mt=` только предвыбирает вариант и меняет хлебные крошки; без него открывается
  вариант по умолчанию (первый по порядку исходного сайта);
- если у товара один вариант, `?mt=` ни на что не влияет и переключатель не рендерится;
- с `/machines/:machineType` доступен переход в каталог с уже применённым фильтром
  («Показать в каталоге: 35 позиций»).

Совместимость товар ↔ тип техники в инвентаре выведена из блоков «АГРЕГАТИРОВАНИЕ» карточек и имеет
статус **PARTIALLY VERIFIED** — это ограничение переносится в интерфейс как формулировка
«агрегатируется с», а не как гарантия совместимости.

## 6. Каталог

### 6.1 Структура страницы

```
breadcrumbs
H1 + короткое описание (для категории — своё)
[поиск]  [сортировка]                     счётчик: «Найдено 23 из 49»
чипы применённых фильтров          [Сбросить всё]
────────────────────────────────────────────────
фасеты (слева, desktop)   |   сетка карточек 3 кол.
```

### 6.2 Фасеты — каждая опирается на реально существующее поле

| Фасет | Поле данных | Значения | Покрытие |
|---|---|---|---|
| Категория | `product.categoryId` | 8 групп | 49/49 |
| Тип техники | `product.machineTypeIds[]` | **только 7 подтверждённых** | 49/49 (PARTIALLY VERIFIED) |
| Цена «от» | `product.priceFrom` | до 50 000 (5) · 50 000–150 000 (18) · 150 000–300 000 (23) · от 300 000 (3) | 49/49, пропусков нет |

Множественный выбор внутри фасета — ИЛИ, между фасетами — И.

**Отклонено при self-review:** фильтры «есть таблица характеристик» (21/49) и «есть видео» (6/49).
Данные реальные, но покупатель не ищет технику по признаку «на странице есть таблица». Оба признака
переехали в бейджи карточки, где они полезны как сигнал полноты данных.

Неподтверждённый тип техники «Экскаватор» в фасете **не появляется** — ни как опция, ни как
скрытая опция с пометкой.

### 6.3 Поиск

Нужен, но минимальный: поле внутри `/catalog`, поиск подстроки без учёта регистра по названию,
категории и типам техники. 49 товаров — библиотека полнотекстового поиска и глобальный поиск в
шапке избыточны. Поиск работает вместе с фасетами и учитывается в счётчике.

### 6.4 Состояния

| Состояние | Поведение |
|---|---|
| Фильтры применены | Чипы над сеткой: «Ковши ✕», «Минипогрузчик ✕», «50 000–150 000 ₽ ✕»; рядом «Сбросить всё» |
| Счётчик | «Найдено N из 49» — всегда виден, в том числе на мобильном на кнопке фильтра |
| Пусто | «По выбранным условиям ничего не найдено» + названы конкретные фильтры, которые стоит снять, + кнопка «Сбросить всё» + ссылка на подбор по типу техники |
| Сброс | Возвращает `/catalog` без query-параметров; на категорийной странице сбрасывает всё, кроме самой категории |
| Сортировка | По цене ↑ / по цене ↓ / по названию. По умолчанию — порядок каталога-источника |

Состояние фильтров синхронизировано с URL (`?cat=&mt=&price=&q=&sort=`), поэтому ссылку на выборку
можно переслать коллеге — для B2B это важнее, чем анимация фильтра.

### 6.5 Карточка товара в выдаче

```
фото 4:3 (или явная техническая заглушка)
Название (до 2 строк, без обрезки посередине слова)
от 195 000 ₽
метки совместимых типов техники (до 2 + «ещё N»)
```

Карточка сравнима без открытия — это главный KEEP из `REFERENCES.md`. Вся карточка — одна ссылка;
отдельной кнопки «Купить» нет.

> **Обновлено на этапе каталога.** Проект ранее планировал на карточке бейджи «Таблица
> характеристик» / «Видео» и 2–3 ключевых параметра. В принятой реализации
> (`src/components/ProductCard.astro`, утверждена визуально на desktop и mobile) их нет:
> служебные бейджи перегружали карточку, а ключевые параметры недоступны единообразно —
> схемы таблиц у товаров разные. Документ приведён в соответствие с принятым кодом, чтобы
> не расходиться с реальностью. Карточка одинакова на главной и в каталоге.

### 6.6 Mobile

- фасеты — в drawer снизу, кнопка «Фильтры (3)» закреплена, в drawer кнопка «Показать 23 товара»;
- карточки в 1 колонку, целевые зоны ≥ 44 px;
- чипы применённых фильтров скроллятся горизонтально;
- сортировка — нативный `<select>`;
- длинные русские названия переносятся, не обрезаются.

## 7. Product Page — один универсальный шаблон

Шаблон один для всех 49 товаров. **Отсутствующий тип данных не создаёт пустой блок** — секция не
рендерится вовсе (без «Информация уточняется», без пустых рамок).

| # | Блок | Условие рендера | Данные |
|---|---|---|---|
| 1 | Breadcrumbs | всегда | категория или тип техники как контекст |
| 2 | Шапка: H1, категория, метки типов техники, «от X ₽», primary CTA «Запросить цену» | всегда (`priceFrom` есть у 49/49) | `name`, `categoryId`, `machineTypeIds`, `priceFrom` |
| 3 | Галерея | всегда; при отсутствии фото — **явная техническая заглушка**, а не чужое фото | `media[]` |
| 4 | Переключатель варианта по типу техники | только если `variants.length > 1` (8 товаров-ковшей) | `variants[]` |
| 5 | Таблица характеристик | `specTables.length > 0` (21 товар) | произвольные колонки, до 12 штук |
| 6 | Цены по вариантам | `priceRawSamples.length > 0` | verbatim-строки источника |
| 7 | Описание | есть текст | фрагменты, PARTIALLY VERIFIED |
| 8 | Агрегатирование / совместимость | `machineTypeIds.length > 0` | формулировка «агрегатируется с» |
| 9 | Преимущества | есть текст | список |
| 10 | Видео | `video != null` (6 товаров) | платформа NOT VERIFIED → пока рендерится только заголовок секции при наличии подтверждённого URL, иначе секции нет |
| 11 | Документы | `documents.length > 0` (сейчас 0) | блок не рендерится ни у одного товара |
| 12 | Похожие товары | только внутри своей категории и ≥ 3 кандидата | `categoryId` |
| 13 | Mock-форма запроса | всегда | предзаполнено название товара и выбранный тип техники |

**Desktop:** блоки 2 и 13 частично объединены — справа липкая панель (цена + CTA + телефон),
слева контент. **Mobile:** липкая нижняя полоса «от X ₽ · Запросить цену».

Таблицы характеристик — несущий элемент страницы, а не приложение к описанию: своя типографика,
табличные цифры, зебра строк, горизонтальный скролл **внутри своего контейнера** (страница по
горизонтали не едет), липкая первая колонка на мобильном.

Вторичные B2B-действия («скачать опросный лист», «техническое задание», «сравнить») **не
добавляются** — данных под них нет; появятся только вместе с реальными документами.

## 8. Служебная страница `/_data-review`

Не входит в навигацию, футер и sitemap. Показывает 13 пунктов DATA_REVIEW с обоими конфликтующими
значениями, URL источников и списком затронутых товаров.

Зачем: честность данных обеспечивается тем, что спорное **не показывается** клиенту, но при этом
не теряется и доступно владельцу для решения одним экраном. В клиентском UI пометок
«DATA_REVIEW» нет.
