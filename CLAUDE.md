Мы создаём отдельный локальный прототип нового сайта компании СТ-ТЕХНИКС.

https://st-technics.ru/

* сохранить значимый публичный контент;
* улучшить каталог;

* хорошо работать на desktop/mobile;

## Стек и команды

Astro 5 (`output: 'static'`), TypeScript, обычный CSS с custom properties — без UI-фреймворков,
без Tailwind, без React/Vue islands. Зависимости: только `astro`, `@astrojs/check`, `typescript`.

```bash
npm run dev            # dev-сервер (localhost:4321)
npm run build           # node scripts/validate-catalog.mjs && astro build
npm run preview         # предпросмотр собранного dist/
npm run typecheck       # astro check (типы + диагностика шаблонов)
npm run lint             # алиас на astro check — отдельного ESLint/Stylelint нет
npm test                 # node:test, без зависимостей: тесты слоя данных (tests/*.test.mjs)
npm run validate:catalog # только проверки целостности каталога (без сборки)
npm run gen:catalog      # пересобрать data/catalog/*.json из data/content-inventory.json
npm run merge:images     # слить fetched-images.json в product-images.json (сети не требует)
npm run check:links      # проверка ссылок в dist/ + обратная проверка всех маршрутов
```

Обязательный минимум перед тем, как считать задачу выполненной: `npm run typecheck`,
`npm test`, `npm run build` (он же прогоняет `validate:catalog`), `npm run check:links`.

Один тест-файл или один тест: `node --test tests/catalog.test.mjs` или
`node --test --test-name-pattern="варианты"` (регэксп по названию теста).

Тесты (`tests/catalog.test.mjs`, `node --test`) проверяют не JSON, а **функции доступа**
(`src/data/catalog.ts`, `src/data/productContent.ts`): ошибка вида «неподтверждённый тип техники
просочился в выборку» не ловится ни типами, ни сборкой — JSON остаётся валидным, страница
собирается, и в UI просто появляется то, чего показывать нельзя. Node сам снимает типы с `.ts`,
поэтому относительные импорты в тестах пишутся с расширением (`../src/data/catalog.ts`), а
JSON-импорты внутри `src/data/*.ts` — с `with { type: 'json' }` (иначе Node их не резолвит;
Astro/Vite такую запись понимают).

**Браузерные инструменты по умолчанию не используются.** Разрешение даётся пользователем разово
под конкретный запрос (так было в запросах №29 и №30). Стандартный путь проверки UI —
статическая сборка + `check-links.mjs`. Если разрешение получено — рабочий инструмент здесь
Playwright MCP (`npm run dev` в фоне → `browser_navigate`/`browser_evaluate`), и overflow
проверяется программно (`scrollWidth <= innerWidth`), а не по скриншоту.

**Экономия токенов**: читай только файлы, относящиеся к текущей задаче, не сканируй весь
репозиторий без необходимости, не перепроверяй уже утверждённый дизайн заново, не используй
Playwright, если визуальная/функциональная проверка её не требует. В рутинных отчётах — кратко,
для длинных задач фиксируй прогресс в файлах проекта (`docs/prototype-progress.md`), а не
полагайся на историю чата.

## Архитектура

Пока это демонстрационный прототип. Не создавай backend, CMS или сложную инфраструктуру без
необходимости — предпочитай структурированные локальные данные, которые позднее можно
подключить к CMS/backend.

Сейчас собирается **68 страниц** (запрос №30):

| Маршрут | Файл | Кол-во |
|---|---|---|
| `/` | `src/pages/index.astro` | 1 |
| `/catalog` | `src/pages/catalog/index.astro` | 1 |
| `/catalog/category/[category]` | одноимённый файл | 8 |
| `/catalog/[product]` | одноимённый файл | **50** (49 видимых + скрытый дубль) |
| `/machines` | `src/pages/machines/index.astro` | 1 |
| `/machines/[machineType]` | одноимённый файл | 7 |

Не реализованы (осознанно, вне объёма запроса №30): `/oplata-i-dostavka`, `/contacts` —
только они остались в списке `PLANNED` в `scripts/check-links.mjs`. Служебная `/_data-review`
(§8 SITE_STRUCTURE) отложена отдельным решением пользователя.

Полная миграция старого каталога сейчас не требуется (решение пользователя от 2026-09-03):
полностью, с реальным контентом, мигрируются только отобранные референсные товарные страницы;
остальной каталог должен быть структурно готов (полноценный `Product`/`ProductVariant`,
рабочие маршруты и UI), но может содержать `UNKNOWN`/плейсхолдеры там, где контент ещё не
добран — это не считается незавершённостью страницы, если инвариант `sourceUrl` и модель
данных соблюдены.

`/catalog` и `/catalog/category/*` — **одна и та же** реализация: движок `CatalogView.astro`,
категорийная страница это он же с зафиксированной категорией. Не заводить второй шаблон.

**Конвейер данных** (важно понимать целиком, а не по одному файлу):

```
data/content-inventory.json      ← сырой слепок с st-technics.ru (источник истины)
        │  npm run gen:catalog (scripts/build-catalog-data.mjs)
        ▼
data/catalog/{categories,machine-types,products,variants}.json  ← сгенерированные из инвентаря
        │
        │  ОТДЕЛЬНАЯ ветка — прямой добор с сайта (scripts/fetch-product-content.mjs,
        │  только по разовому разрешению; свой провенанс, НЕ из инвентаря):
        ▼
data/catalog/product-content.json   ← тексты + таблицы характеристик со страниц источника
data/catalog/fetched-images.json    ← сырой результат скачивания картинок
        │  npm run merge:images (scripts/merge-product-images.mjs)
        ▼
data/catalog/product-images.json    ← итоговый манифест изображений
        │  импортируются как JSON-модули с `with { type: 'json' }`
        ▼
src/data/catalog.ts        ← ЕДИНСТВЕННАЯ точка доступа к каталогу и вариантам
src/data/productContent.ts ← тексты и таблицы (getDescriptionSections/getSpecTables/…)
src/data/productImages.ts  ← изображения (getCardImage/getProductImages/…)
src/data/site.ts           ← контент уровня сайта (BRAND, CONTACTS, TRUST_FACTS, NAV) — тоже
                             вручную сверен с инвентарём, с комментарием источника у значения
        │
        ▼
src/pages/*.astro, src/components/*.astro
```

`gen:catalog` порождает файлы **только** из инвентаря — он затирает `products.json` и
`variants.json`, но НЕ трогает `product-content.json` и `product-images.json`. Поэтому добранный
с сайта контент не теряется при регенерации, и наоборот: правки в инвентаре требуют
`npm run gen:catalog`, а не ручного редактирования сгенерированных файлов.

`tsconfig.json` объявляет алиасы `@data/*`, `@components/*`, `@layouts/*`, `@types/*` — они
**не подключены** ни в один резолвер (нет `vite-tsconfig-paths`, `astro.config.mjs` их не
трогает) и нигде в коде не используются. Не начинать использовать: импорт по такому алиасу
не разрешится. Все импорты в проекте — относительные пути.

Страницы и компоненты **никогда не импортируют `data/**/*.json` напрямую** — только через
функции `src/data/catalog.ts` (`getCategories`, `getVisibleMachineTypes`, `getProducts`,
`getProduct`, `getProductVariants`, `getPreselectedVariant`, `getProductsByCategory`,
`getProductsByMachineType`, …) и `src/data/productContent.ts`. Это осознанная граница:
при подключении реальной CMS/API поменяется только этот файл, типы и компоненты — нет
(см. `docs/DATA_MODEL.md` §10). Типы каталога — `src/types/catalog.ts`.

Ключевые инварианты данных (проверяются `scripts/validate-catalog.mjs`, `npm test` и частью
самих функций `catalog.ts`):

* один товар = один canonical `Product` (не дублируется на тип техники);
* `MachineType.confirmed === false` (сейчас — «Экскаватор», DR-10) никогда не попадает в
  пользовательский UI — единственный легальный путь получить список типов техники для UI
  это `getVisibleMachineTypes()`, не сырой JSON. Это касается и **вариантов**: у скрытого типа
  есть 3 варианта с реальными ценами, `getProductVariants()` их отфильтровывает, а
  `getAllVariantsUnsafe()` — только для служебных нужд;
* скрытые дубли товаров (`visible:false`) не входят в каталог, но доступны по прямому URL —
  поэтому `getStaticPaths` товара использует `getAllProductsUnsafe()` (50 маршрутов), а все
  листинги — `getProducts()` (49);
* `ProductVariant.machineTypeId` **не уникален внутри товара** (у «Ковш планировочный» два
  варианта на экскаватор-погрузчик, у «Ковш универсальный» три на мини-экскаватор) — различает
  их только обязательный `label`, уникальность которого проверяется валидатором;
* таблица характеристик существует **только при реально захваченных строках**; `colspan`/
  `rowspan` источника сохраняются дословно и рендерятся теми же атрибутами — «выпрямление»
  таблицы сдвигает технические значения (на этом уже терялось 165 строк, см. запрос №30);
* у каждого `Product` и `Variant` обязателен `sourceUrl`; расхождения источника зафиксированы
  в `data/content-inventory.json → dataReviewRequired` (сейчас 15 записей: DR-01…DR-12,
  DR-14…DR-16; `DR-13` существует только в `docs/DATA_MODEL.md` — см. `docs/HANDOFF.md` §5)
  и не «исправляются» на своё усмотрение. Новое расхождение → новый номер DR, а не правка данных.

**Изображения товаров**: `data/catalog/product-images.json` (327 записей на 50 товаров), доступ
только через `src/data/productImages.ts`. В UI используются исключительно записи с
`verificationStatus: "VERIFIED"`; карточное/hero-изображение выбираются по `role` в манифесте,
не автоматическим правилом «самое большое». `fit`/`objectPosition` идут из манифеста;
`object-fit: contain` требует белого фона media-контейнера (`.product-card__media--contain`,
`.gallery__stage`), а не `--bg-muted` — иначе видны серые боковые полосы.

Поле `pickMethod` различает происхождение карточного кадра и **не должно смешиваться**:
у 8 товаров Homepage карточка выбрана визуальным просмотром каждого кадра (поля нет), у
остальных 42 — по явному правилу `"source-gallery-order"` (первый кадр галереи источника,
`fit: contain`). Второе честнее считать непроверенным глазами: если карточка выглядит плохо,
это ожидаемое место для правки.

**Слои страницы** (`src/layouts/Base.astro`): один общий layout, один `<head>` со всеми favicon
и `<meta>`-тегами (не дублировать на страницу), `<Header>` / `<slot>` / `<Footer>` /
`<FloatingTelegram>` в этом порядке. `FloatingTelegram.astro` — глобальный плавающий виджет,
не завязан на контент конкретной страницы.

**Стили**: `src/styles/tokens.css` (design tokens — палитра, типографика, сетка, все
PROVISIONAL до подтверждения фирменного стиля) + `src/styles/base.css` (reset, `.container`,
`.card-grid`, кнопки, фокус-стили). Специфика секций живёт в scoped `<style>` внутри самих
`.astro`-компонентов/страниц — общесайтовых утилит-классов сверх этого нет.

**Иконки** (`src/components/icons/`): собственные inline SVG, геометрия выведена вручную
(не скопирована из внешних библиотек) — намеренно, поскольку браузерные инструменты не
используются и сложные заимствованные path нельзя визуально перепроверить. Telegram-ассеты
частично статические файлы в `public/icons/*.svg` — не единый переиспользуемый компонент для
floating и footer размещений, у них разная визуальная логика (см. `CONTACTS.telegram.floating`
/ `.footer` в `src/data/site.ts`, DR-04).

## Модель контентной целостности

Эти ограничения обязательны и *не* переопределяются обычными запросами на редизайн — только
явным решением пользователя:

* цены, характеристики, клиенты, сертификаты, телефоны, адреса, сроки, гарантии, условия
  доставки, технические/производственные показатели — никогда не выдумываются;
  отсутствующее значение — `UNKNOWN` во внутренних данных/документации, в UI — нейтральный
  плейсхолдер («Цена по запросу» и т. п.), не правдоподобная догадка;
* при противоречии источников — оба значения сохраняются, оба source URL сохраняются,
  какое из них «правильное» не выбирается самостоятельно (`DATA_REVIEW_REQUIRED`);
  список открытых противоречий — `data/content-inventory.json → dataReviewRequired` (DR-01…);
* можно свободно улучшать UX-copy, структуру, заголовки интерфейса, CTA — но не менять
  технический или коммерческий смысл;
* никаких случайных/AI-сгенерированных изображений вместо реальных фото продукции;
* все формы прототипа — только mock (без сетевых запросов, без реальной отправки).

Подробные формулировки — `.claude/rules/content-integrity.md`, `.claude/rules/safety.md`,
`.claude/rules/design.md`, `.claude/rules/catalog-data.md`, `.claude/rules/testing.md` (уже
подключаются автоматически как project rules — не дублировать их содержимое сюда).
